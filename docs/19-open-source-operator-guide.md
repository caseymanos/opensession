# Open-source operator guide

This is the reproducible setup and recovery path for OpenSession. It separates commands that are safe in a fresh clone from commands that mutate remote providers. Examples use placeholders only; generated IDs, credentials, recipient addresses, private evidence, and owner-specific paths must never be committed.

## Safety model

| Command class | Examples | Effect |
|---|---|---|
| local/read-only | install, build, tests, `cloudflare:plan`, `cloudflare:status`, Airtable `schema:check` | no provider data mutation |
| preview mutation | `cloudflare:provision:preview`, Airtable `schema:bootstrap --apply`, guarded deploy/seed | changes isolated preview resources only |
| production mutation | lower-level commands with two-part confirmation | changes isolated production resources only |

Run remote commands only from a clean, reviewed commit and only after selecting the intended account and environment. Do not run a remote command merely to validate this guide; the local and fixture gates below require no secrets.

## Fresh clone and local development

Required versions:

- Node.js `26.7.0` from `.nvmrc`/`.node-version`;
- pnpm `10.34.5` from `package.json`;
- Wrangler `4.120.0` from the immutable lockfile.

```bash
git clone https://github.com/caseymanos/opensession.git
cd opensession
nvm use
corepack enable
pnpm install --frozen-lockfile
pnpm exec wrangler --version
pnpm dev
```

`pnpm dev` builds the React assets and starts the Worker on `http://localhost:8787` with local D1, R2, Durable Object, Queue, Workflow, and Analytics Engine bindings. The shell and deterministic fixture routes do not require `.dev.vars`. Wrangler warns about missing provider secrets because the same binding contract is used in every environment; that warning is expected while provider-backed routes remain unused.

For an explicit disposable local D1 migration rehearsal:

```bash
pnpm exec wrangler d1 migrations list DB \
  --local --config workers/app/wrangler.jsonc
pnpm exec wrangler d1 migrations apply DB \
  --local --config workers/app/wrangler.jsonc
```

Wrangler stores local state under its ignored local directory. Delete or replace local state only when you intentionally want a disposable reset; never apply a cleanup command to a remote database.

Local product surfaces:

```text
http://localhost:8787/
http://localhost:8787/fixtures/agenda/published?view=list
http://localhost:8787/fixtures/public-cfp/interactive
http://localhost:8787/openapi.json
http://localhost:8787/docs/api
```

## Configuration and secrets

`.env.example` is the complete name-only contract. Copy it only when a local provider-backed path is required:

```bash
cp .env.example .dev.vars
chmod 600 .dev.vars
```

Rules:

- local secrets live only in ignored `.dev.vars`;
- remote Worker secrets are installed with Wrangler's secret command against an ID-complete ignored config;
- `AIRTABLE_SCHEMA_PAT` is operator-only and is never deployed to the Worker;
- base IDs and client-visible Turnstile site keys are non-secret but environment-specific and stay out of the public config when generated by provisioning;
- private recipient inputs exist only in the guarded deployment process;
- `.cloudflare/` inventory and rendered configs are ignored, owner-readable, and never copied into source or evidence.

The committed `workers/app/wrangler.jsonc` is the safe binding-name contract. It deliberately contains local IDs and remote placeholders, not generated D1 or account identifiers.

## Cloudflare preview provisioning

Prerequisites are an authenticated Wrangler session or a least-privilege process token and a selected, isolated Airtable preview base ID. Plan and status are read-only:

```bash
AIRTABLE_PREVIEW_BASE_ID=app_REPLACE_ME pnpm cloudflare:plan
AIRTABLE_PREVIEW_BASE_ID=app_REPLACE_ME pnpm cloudflare:status
```

Review the complete diff, account, environment, and names before apply. The idempotent preview apply creates only missing application-owned resources:

```bash
AIRTABLE_PREVIEW_BASE_ID=app_REPLACE_ME \
pnpm cloudflare:provision:preview
```

The provisioner resolves and privately records generated IDs for:

- Worker/static assets: `sessionbox-killer-preview`;
- D1: `sessionbox-killer-preview`;
- private R2: `sessionbox-killer-uploads-preview`;
- email and projection-repair queues plus their dead-letter queues;
- reserved webhook-delivery and integration-export producer queues;
- `AgendaCoordinator` and `BaseAuthority` SQLite Durable Objects;
- `TaskReminderWorkflow`;
- Analytics Engine and Cron/binding configuration.

The committed config is more conservative than the private rendered deployment: email and other external features remain off, and the preview allowlist is empty. Provisioning does not bootstrap Airtable, install application secrets, seed demo data, or prove a provider.

## Airtable schema and probe

OpenSession's authoritative Airtable contract is schema **v10**, defined in `packages/data/src/airtable/schema-definition.ts`, with 31 application-managed tables. Use a preview base that no other environment uses.

Required operator-only values:

```dotenv
AIRTABLE_ENVIRONMENT=preview
AIRTABLE_PREVIEW_BASE_ID=app_REPLACE_ME
AIRTABLE_PAT=pat_REPLACE_ME
AIRTABLE_SCHEMA_PAT=pat_REPLACE_ME
```

Build and read drift before any write:

```bash
pnpm --filter @sessionbox-killer/domain build
pnpm --filter @sessionbox-killer/data airtable \
  schema:check --environment preview
```

Bootstrap is additive and explicit. It may create missing managed tables/fields, but it never deletes, renames, or silently converts existing provider schema:

```bash
pnpm --filter @sessionbox-killer/data airtable \
  schema:bootstrap --environment preview --apply
pnpm --filter @sessionbox-killer/data airtable \
  schema:check --environment preview
pnpm --filter @sessionbox-killer/data airtable \
  probe --environment preview --apply
```

An incompatible table type, field type, linked-record target, or primary field fails before the first bootstrap write. The probe uses stable synthetic IDs and is safe to repeat against the selected preview base.

Production schema bootstrap and probe require both `--confirm-production` and `AIRTABLE_PRODUCTION_CONFIRM=production`. Preview and production base IDs are rejected when equal.

## D1 migrations

Migrations in `migrations/` are ordered, forward-only, and must remain compatible with the previous Worker during the release window. Validate locally first:

```bash
pnpm exec vitest run scripts/d1/schema.test.ts
pnpm exec wrangler d1 migrations list DB \
  --local --config workers/app/wrangler.jsonc
pnpm exec wrangler d1 migrations apply DB \
  --local --config workers/app/wrangler.jsonc
```

For preview, the guarded deploy uses its ignored ID-complete rendered config and applies pending migrations before publishing the Worker. To inspect without applying:

```bash
pnpm exec wrangler d1 migrations list DB --remote \
  --config .cloudflare/wrangler.preview.json
```

The rendered filename is private inventory produced by the provisioner; confirm its actual path rather than inventing or committing an ID-complete config. Wrangler makes a backup around migration application and rolls back the migration that fails. A later Worker or smoke failure does not reverse an already successful additive migration.

The complete migration inventory and recovery constraints are in [`migrations/README.md`](../migrations/README.md).

## Guarded demo seed

The committed seed manifest is `workers/app/src/demo/seed-manifest.json`. It contains stable synthetic identifiers, a digest, operation count, and asset count; it contains no real recipients or provider IDs.

After the complete D1 migration chain, matching Worker SHA, Airtable schema v10, and authority lineage are active, run the preview bootstrap with process-only values:

```bash
AIRTABLE_PREVIEW_BASE_ID=app_REPLACE_ME \
AIRTABLE_PAT=pat_REPLACE_ME \
DEMO_OWNER_EMAIL=owner@example.test \
pnpm cloudflare:demo:bootstrap --environment preview
```

The bootstrap accepts only an empty base or the exact managed demo roots. It creates the canonical roots through `AirtableCommandStore`, registers their lineage in D1, synchronizes through `BaseAuthority`, and applies the digest-bound 139-operation snapshot plus four private assets. Interrupted runs resume the same durable operation and private authorization. Use `--restart-failed` only after correcting a permanent authoritative conflict.

Production additionally requires `--confirm-production` and `DEMO_PRODUCTION_CONFIRM=production`. Normal demo reset remains an authenticated in-product operation; there is no public reset or arbitrary seed endpoint.

### Post-reset demo role identities

The exact AI Engineer Summit demo has a separate owner-controlled post-reset step for its organizer, reviewer, and speaker sign-in aliases. The fixture intentionally contains no recipient aliases. Supply all three addresses only in the same-origin request body at runtime; do not place them in source, shell history, screenshots, logs, tickets, or deployment configuration.

With email still disabled, an authenticated organization owner first reads `GET /api/events/ai-engineer-summit/demo/role-identities/plan`. The response names the three supported identities and returns the current confirmation and fixture fingerprint. Submit those values unchanged to `POST /api/events/ai-engineer-summit/demo/role-identities/provision` with the current CSRF token, one fresh `Idempotency-Key`, and exactly these entries:

```json
{
  "confirmation": "<confirmation from plan>",
  "fixture_fingerprint": "<fingerprint from plan>",
  "identities": [
    { "role": "organizer", "email": "owner+organizer@example.test" },
    { "role": "reviewer", "email": "owner+reviewer@example.test" },
    { "role": "speaker", "email": "owner+speaker@example.test" }
  ]
}
```

Replace the example addresses in process memory only. Provisioning is atomic, does not enqueue email, preserves plus tags, rejects normalized collisions or fixture drift, and returns only non-reversible identity IDs. Reusing the same idempotency key with the same contract returns the stored replay receipt; a changed contract fails closed. If a deliberate demo reset clears auth identity state, read a fresh plan and repeat this step with a fresh key before enabling the separately approved bounded send window.

## Deploy and verify

Preview:

```bash
AIRTABLE_PREVIEW_BASE_ID=app_REPLACE_ME pnpm cloudflare:deploy:preview
pnpm cloudflare:smoke:preview
pnpm cloudflare:status
```

The guarded deploy revalidates inventory and Airtable readiness, applies pending migrations, builds the web assets, deploys the ID-complete configuration, records exact source/version/deployment receipts privately, and checks shell/liveness/readiness. It never labels an adjacent deployment as last-known-good.

Production intentionally has no convenience package shortcut. It requires both confirmation mechanisms and an explicit environment:

```bash
AIRTABLE_PRODUCTION_BASE_ID=app_REPLACE_ME \
CLOUDFLARE_PRODUCTION_CONFIRM=production \
node scripts/cloudflare/private-deploy.mjs \
  --build-web deploy \
  --environment production \
  --confirm-production
```

Domain, DNS, provider, migration, seed, and deployment evidence belongs in the private release system. Public documentation records contracts and commands, never generated identifiers or credentialed transcripts.

## Email modes

| Environment | Committed mode | Feature flag | Recipient behavior |
|---|---|---|---|
| local | `sink` | off by default | no provider delivery |
| preview | `allowlist` with empty list | off | guarded deploy may privately inject exactly one approved address |
| production | `allowlist` with empty list | off | guarded acceptance deploy may privately inject one to six approved addresses |

`live` is an operational state after a separate reviewed readiness decision; it is not the public repository default. Never change production to sink while claiming delivery and never add an address to Git.

Preview allowlist injection must use the private launcher so the address is removed from build and Wrangler child environments and suppressed from output:

```bash
AIRTABLE_PREVIEW_BASE_ID=app_REPLACE_ME \
EMAIL_PREVIEW_RECIPIENT=approved@example.test \
node scripts/cloudflare/private-deploy.mjs \
  --build-web deploy --environment preview
```

Before any live decision, prove the verified sender/reply route, signed Resend callback, inbox receipt, bounce/complaint suppression, deduplication, bounded retries, and dead-letter queue. The full release procedure is in [`docs/08-delivery-runbook.md`](./08-delivery-runbook.md).

## Dual-store repair

Airtable owns conference-program records; D1 owns the operational ledger and query projections. There is no distributed transaction and no supported path that makes D1 an independent business-data writer.

### Command outcome states

1. `pending`: the authority has durably leased the intent but no provider result is committed.
2. `committed`: the Airtable result, D1 projection, idempotency response, audit row, and outbox changes are durable.
3. `committed_with_repair`: Airtable committed but the atomic D1 projection failed; return/replay the stored response and repair D1 without replaying Airtable.
4. `unknown`: an ambiguous provider result must be reconciled by stable command markers before another mutation.
5. `failed`: the authority rejected or terminally failed before a committed business result.

`BaseAuthority` stores provider attempts and the original response in SQLite before projection. Its alarm and the projection-repair queue call `recoverPending()`; identical retries return the stored response. Direct Airtable edits converge when webhook-cursor ingestion or the bounded full scan is invoked. The current public config does not attach an Airtable webhook or reconciliation Cron, so explicit full-scan evidence is a release gate. Protected lifecycle tampering fails closed rather than being adopted.

### Read-only diagnosis

Use a selected environment's ID-complete private config:

```bash
pnpm exec wrangler d1 execute DB --remote \
  --config .cloudflare/wrangler.preview.json \
  --command "SELECT status, COUNT(*) AS count FROM projection_repairs GROUP BY status ORDER BY status"

pnpm exec wrangler d1 execute DB --remote \
  --config .cloudflare/wrangler.preview.json \
  --command "SELECT status, COUNT(*) AS count FROM idempotency_keys GROUP BY status ORDER BY status"
```

Do not dump payload, recipient, token, or private URL columns into logs or tickets. Correlate only safe request/operation IDs and aggregate status.

### Recovery decision

- Pending/leased repair with a live queue: wait for the bounded retry and confirm readiness returns to ready.
- Dead/failed repair: disable the affected write feature, retain Airtable as authority, record safe correlation IDs, and diagnose the projector/contract before replay.
- Unknown Airtable outcome: never resend blindly; use the stable command ID/hash and authority recovery path to read back the provider marker.
- Direct organizer edit: allow the reconciler to adopt safe managed-content changes with a new source version; protected lifecycle drift requires manual correction in Airtable.
- R2 mismatch: do not create a D1-only file record; reauthorize and finalize the exact object version or remove the incomplete object through the private recovery process.

Recovery is complete only when pending repairs are zero, authority readiness is restored, the original response still replays, and a source-version/content-hash comparison matches Airtable.

## Rollback and disaster recovery

Worker rollback changes code and Worker configuration only. It does not reverse D1 migrations, Airtable schema/data, R2 objects, Queue contents, Workflows, or Durable Object storage.

Preview rollback requires an explicit recent version from status/history:

```bash
pnpm cloudflare:status
chmod 600 .cloudflare/lkg.preview.json
pnpm cloudflare:rollback:preview -- --lkg-receipt .cloudflare/lkg.preview.json
```

The receipt must explicitly name the independently verified version and deployment plus its source commit/tree, script ETag, full non-secret resource fingerprint, verifier, and timestamp. The command rereads every safety binding and resource before activation; any true or missing dangerous flag, nonempty email allowlist, wrong source/resource, split/ambiguous deployment, or unavailable target is a hard stop. Do not substitute “previous” or list position for this receipt.

Production rollback adds the two production confirmations. The guard rejects split deployments, missing resources, and invalid version IDs, verifies the requested version is active, then repeats release smoke. Cloudflare may reject a rollback when a bound resource was deleted/changed or a Durable Object lifecycle changed; do not delete release resources during the rollback window.

Before a remote migration or risky release, capture a D1 bookmark and provider export in the private release system:

```bash
pnpm exec wrangler d1 time-travel info <DATABASE_NAME> \
  --config .cloudflare/wrangler.production.json
pnpm exec wrangler d1 export <DATABASE_NAME> --remote \
  --config .cloudflare/wrangler.production.json \
  --output <PRIVATE_BACKUP_PATH>
```

D1 Time Travel restore overwrites the database in place and cancels in-flight queries. It is a last-resort, separately approved production mutation:

```bash
pnpm exec wrangler d1 time-travel restore <DATABASE_NAME> \
  --config .cloudflare/wrangler.production.json \
  --bookmark <BOOKMARK>
```

Record the previous bookmark returned by restore so the restore itself can be undone. Cloudflare's current references are [D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/), [D1 migration commands](https://developers.cloudflare.com/d1/wrangler-commands/), and [Worker rollbacks](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/).

Airtable schema changes are additive during the release window. Export the selected base before bootstrap/seed, retain the timestamp and checksum privately, and restore into the same isolated environment only with an approved data-recovery plan. After any D1 or Airtable recovery, run full reconciliation before re-enabling writes.
